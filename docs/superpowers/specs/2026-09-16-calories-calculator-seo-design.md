# Дизайн: SEO і швидкість сторінки калькулятора калорій

- Дата: 2026-09-16
- Сторінка: `/calcs/calories-calculator` (`app/calcs/calories-calculator/page.tsx`)
- Статус: дизайн затверджено користувачем 16.09.2026, реалізація трьома PR
- Гілка: `feat/calories-calculator-seo`

## 1. Контекст і мета

Сторінка калькулятора калорій дає близько 87% усіх пошукових кліків сайту
(614 із 708 за період на скріншоті Search Console). Середня позиція 7,2, CTR 1,4%,
43 041 показ. Головні запити стоять на позиціях 4-10:

| Запит | Позиція | CTR |
|---|---|---|
| калькулятор калорій | 9,5 | 1,8% |
| калькулятор калорій для схуднення | 7,0 | 2,7% |
| калькулятор дефіциту калорій | 7,5 | 8,8% |
| розрахунок калорій | 5,6 | 6,8% |
| як розрахувати калорії для схуднення | 2,5 | 17,6% |

Менше 2% показів припадає на топ-10 запитів, решта це довгий хвіст
("скільки калорій потрібно жінці 30 років" тощо).

PageSpeed Insights, мобільний: performance 69, FCP 2,2 с, LCP 6,8 с, TBT 230 мс, CLS 0.

Мета робіт:

1. LCP на мобільному не більше 2,5 с у лабораторному тесті PSI, performance не менше 85.
2. Форма калькулятора видима без прокрутки на екранах 360-412 px.
3. Сторінка закриває інтент запитів "дефіцит", "норма калорій", "КБЖВ": показує BMR,
   норму, цільові калорії для трьох цілей і БЖВ, містить таблиці норм і дефіциту.
4. Через 4-6 тижнів після деплою: позиція за "калькулятор калорій" краща за 7,
   за "калькулятор дефіциту калорій" краща за 5, CTR сторінки не менше 3%.

## 2. Діагноз

- **LCP-елемент це декоративне hero-фото** `bg-hero.webp` (264 px заввишки на мобільному).
  Файл важить 8 KB і завантажується за 0,4 с, але у трейсі Lighthouse "render delay"
  становить 4,3 с із 6: перший кадр малюється лише після гідратації React і виконання
  двох скриптів Google Analytics. Симуляція slow 4G і 4x CPU перетворює це на 6-8 с.
- **Google Analytics у критичному шляху.** `components/GoogleAnalytics.tsx` через
  `next/script` створює `<link rel="preload" as="script">` з високим пріоритетом на старті,
  URL містить пробіли й перенос рядка (`gtag/js?%20%20%20id=...`). Два скрипти GA
  важать 285 KB, це 35% байтів сторінки.
- **Шрифти.** У `app/globals.css` `@import` Poppins стоїть після правил Tailwind, тому
  браузер його ігнорує; Poppins і так не має кирилиці. Inter підключено лише з
  сабсетом latin, кириличний файл не в preload і підвантажується після CSS.
- **Перший layout важкий:** 234 мс без throttling для 355 DOM-елементів.
- **Форма далеко від верху:** на мобільному перед нею hero, три вкладки, H2 і два абзаци.
- **Інтент закрито частково:** конкуренти в топі показують BMR, цільові калорії, БЖВ;
  наша сторінка видає одне число і пропонує рахувати дефіцит вручну.
- **Поп-ап Sytno** (`SurveyPopup.tsx`) через 10-15 с накриває контент повноекранним
  оверлеєм на всіх сторінках `/calcs`.
- **Sitemap:** усі 52 URL мають `lastmod` рівний часу запиту, `changefreq: always`,
  `priority: 1`. Google такі дані ігнорує; стара версія title сторінки ІМТ досі в індексі.

## 4. PR 1: швидкість і UX

### 4.1 Макет tool-first

Стосується тільки `app/calcs/calories-calculator/page.tsx`. Порядок DOM однаковий
для всіх брейкпоінтів:

1. хлібні крихти;
2. H1;
3. один рядок підводки ("Введіть дані і отримайте норму, дефіцит і БЖВ за 10 секунд");
4. картка калькулятора (`CaloriesCalcList` + результат) і кнопки `ButtonGroup`;
5. H2 "Розрахунок денної норми калорій онлайн" і опис (`CaloriesDescription`);
   на десктопі це правий стовпчик поруч із карткою;
6. вкладки інших калькуляторів (`CalcTitle`) під блоком картки й опису;
7. FAQ, байлайн, JSON-LD.

Мобільний (менше `md`): hero без фото, суцільний фон `#2E2F42` (колір градієнта
без прозорості), вертикальні відступи 16-20 px, H1 `text-3xl`. Підказка
"переміщуйте повзунок або введіть дані вручну" стає одним рядком дрібного тексту в картці.

Десктоп (`md` і більше): фото повертається як CSS-фон секції hero:
клас `md:bg-hero-photo` у `tailwind.config.js` =
`linear-gradient(...), url('/bg-hero.webp')`, плюс `bg-cover bg-center`.
Компонент `<Image fill priority>` із цієї сторінки прибираємо, тож на мобільному
фото не завантажується взагалі. Форма і опис лишаються у два стовпчики.

Інші сторінки калькуляторів у PR 1 не змінюються.

### 4.2 Google Analytics після LCP

- `components/GoogleAnalytics.tsx`: обидва `<Script>` зі `strategy="lazyOnload"`,
  правильний URL `https://www.googletagmanager.com/gtag/js?id=${ga_id}`,
  компонент нічого не рендерить, якщо `ga_id` не заданий.
- Компонент переносимо з `<head>` у `<body>` кореневого layout (рекомендація Next для
  App Router).
- Дубльований `ToastContainer` у `components/Header.tsx` видаляємо, лишається один
  у кореневому layout.

Компроміс: `lazyOnload` вантажить GA після події `load`, тому сесії коротші за 1-2 с
не потраплять у статистику.

### 4.3 Шрифти

- `app/layout.tsx`: `Inter({ subsets: ['latin', 'cyrillic'], display: 'swap', variable: '--font-inter' })`,
  клас `inter.variable` на `<html>`, `inter.className` лишається на `<body>`.
- `app/globals.css`: видалити `@import` Poppins і `font-family: 'Poppins'` у правилі `body`.
- `tailwind.config.js`: `fontFamily.poppins = ['var(--font-inter)', 'system-ui', 'sans-serif']`,
  тож усі наявні класи `font-poppins` продовжують працювати і рендерять Inter.

Візуальна зміна: елементи з `font-poppins`, які досі показувались системним шрифтом,
показуються Inter.

### 4.4 Поп-ап стає контекстним CTA

- Видалити `components/calcs-page/SurveyPopup.tsx` і `app/calcs/layout.tsx`
  (єдине призначення layout було рендерити поп-ап).
- У `CaloriesCalcFormula` після появи результату показувати рядок
  "Під вашу норму N ккал застосунок Sytno складе меню на день" і посилання
  на `https://nutriday.com.ua/...` з наявними UTM. Без оверлею і без таймера.
- Сторінки ІМТ і жиру зберігають наявну кнопку "Склади своє меню" у `ButtonGroup`.

Компроміс: менше примусових показів Sytno, натомість клік із наміром.

### 4.5 metadataBase, title template, og:image

- Кореневий layout: `metadataBase: new URL('https://gym-adrenalin.com.ua')`,
  `title: { default: 'Тренажерний зал Адреналін у Тернополі', template: '%s | Adrenalin Gym' }`.
- Три калькулятори і пости блогу (`generateMetadata`) переходять на
  `title: { absolute: ... }`, щоб суфікс не обрізав довгі заголовки.
  Головна лишає власний title через `absolute`.
  Заголовки розділу `/learn` отримують суфікс; частина з них довша за 60 знаків
  і буде обрізана Google, це прийнятно і налаштовується окремо.
- `app/calcs/calories-calculator/opengraph-image.tsx` через `ImageResponse` 1200×630:
  фон `#2E2F42`, акцент `#f97316`, текст "Калькулятор калорій онлайн",
  підзаголовок "норма на день · дефіцит для схуднення · БЖВ", домен.
  Кириличний шрифт: `assets/fonts/Inter-Bold.ttf` у репозиторії, використовується лише
  під час збірки.
- У metadata сторінки калорій: `twitter: { card: 'summary_large_image' }`.

### 4.6 Sitemap

`app/sitemap.ts`:

- статичні маршрути з `const/routeSitemap.ts`: для `/calcs/*` `lastModified = CALC_DATE_MODIFIED`,
  для решти константа `SITE_CONTENT_LASTMOD = '2026-08-29'` (дата останнього контентного
  коміту; оновлюється вручну при змінах статичних сторінок);
- пости блогу: `lastModified = createdAt` (у схемі є `timestamps: true`;
  `updatedAt` не підходить, бо змінюється при кожному перегляді і лайку);
- поля `changeFrequency` і `priority` прибираємо, Google їх не читає.

### 4.7 Перевірка PR 1

- `npm run build` і `npm run lint` без помилок.
- Локальна production-збірка і Lighthouse mobile до і після: LCP-елемент має стати
  текстовим (H1), спостережуваний FCP і LCP мають зменшитися.
- Скріншоти 412×915 і 360×640: форма видима без прокрутки.
- `curl` до localhost: og:image, twitter:card присутні; запит gtag у мережевому журналі
  Lighthouse іде після події load.
- Після деплою: PSI, Rich Results Test, запит на переіндексацію в Search Console.

## 5. PR 2: контент і результат

### 5.1 Чистий модуль розрахунку `lib/calories.ts`

Функції без побічних ефектів, покриті unit-тестами (vitest, `npm test`):

- `bmrMifflin({ sex, weightKg, heightCm, age })`;
- `tdee(bmr, activityFactor)`;
- `targets(tdee)` повертає `{ loss20, loss15, loss10, maintain, gain10, gain15 }`,
  округлення до 10 ккал;
- `macros(kcal, weightKg, goal)`: білок 1,8 г/кг для схуднення, 1,6 для підтримки,
  2,0 для набору (ISSN 2017); жири 25% калорійності (ВООЗ 15-30%), вуглеводи решта,
  не менше 0;
- `safeMinimum(sex)`: 1200 ккал для жінок, 1500 для чоловіків; результат нижче межі
  позначається прапорцем для попередження.

Контрольний приклад збігається з FAQ: жінка 30 років, 170 см, 65 кг, помірна активність:
BMR 1401, норма 2172, дефіцит 15% 1846.

### 5.2 Форма і результат

- У форму додається вибір цілі: Схуднути (за замовчуванням), Підтримати, Набрати.
- Новий клієнтський компонент `CaloriesResult.tsx`: BMR, норма, таблиця шести цільових
  значень із підсвіченою ціллю, БЖВ у грамах для обраної цілі, попередження нижче
  безпечного мінімуму, контекстний CTA Sytno (переїжджає сюди з PR 1). `aria-live="polite"`.
- Ліміти: вік 14-100, зріст 120-230, вага 30-250 (input, range, yup).
- `CaloriesCalcFormula.tsx` замінюється на `CaloriesResult.tsx`.

### 5.3 Контентні блоки (серверні, індексовані)

- `CaloriesNormTable.tsx`: H2 "Норма калорій на день для жінок і чоловіків".
  Таблиця: вік 18-30, 31-50, 51-70; активність низька 1,2, помірна 1,55, висока 1,725;
  два набори колонок для еталонів "жінка 165 см 65 кг" і "чоловік 178 см 80 кг".
  Числа рахуються через `lib/calories.ts`, щоб збігалися з калькулятором.
- `CaloriesDeficitTable.tsx`: H2 "Дефіцит калорій для схуднення: скільки віднімати".
  Приклад для норми 2000 ккал: 10, 15, 20% → ккал на день → дефіцит → орієнтовна
  втрата ваги за тиждень із розрахунку 7700 ккал на 1 кг жиру. Правила: не нижче
  1200/1500 ккал, не більше 0,5-1 кг за тиждень, перерахунок після кожних 4-5 кг.
- FAQ: додати "Що таке BMR і чим він відрізняється від норми калорій?" і
  "Скільки білка потрібно на день?". JSON-LD FAQPage формується з того ж масиву.
- `CalcByline.tsx`: дисклеймер "Розрахунки орієнтовні і не замінюють консультацію
  лікаря чи дієтолога. За хронічних захворювань, вагітності або віку до 18 років
  узгодьте раціон із фахівцем." Показується на всіх трьох калькуляторах.
- `CaloriesDescription.tsx`: прибрати дублювання з новими блоками.

## 6. PR 3: довіра і посилання

### 6.1 Рейтинг калькулятора

- `CalcRating.tsx` (клієнт): "Чи корисний калькулятор?", пʼять зірок, після голосу
  "Дякуємо! Середня оцінка X з Y голосів". Один голос на браузер (localStorage),
  оптимістичне оновлення.
- API `app/api/calc-rating/[calcId]/route.ts`: GET повертає `{ average, count }`,
  POST `{ value: 1-5 }` додає голос. Моделі: `CalcRating { calcId, sum, count }` і
  `CalcRatingVote { calcId, ipHash, createdAt }` із TTL-індексом 24 години для захисту
  від повторів з однієї адреси.
- Сторінка калорій переходить на ISR: `export const revalidate = 3600`, рейтинг читається
  на сервері і потрапляє в JSON-LD `aggregateRating` (`ratingValue` з одним знаком,
  `bestRating` 5) лише коли голосів не менше 5.
- Помилка API: віджет ховається, JSON-LD без `aggregateRating`.

### 6.2 Внутрішні посилання

- Головна, `components/main-page/AboutCalc.tsx`: пряме посилання
  "Калькулятор калорій для схуднення" на `/calcs/calories-calculator` поряд із кнопкою хабу.
- Описи ІМТ і жиру: речення з посиланням "розрахуйте денну норму калорій".
- `/learn/nutrition/*`: анкори "нашого калькулятора" і "можна тут" замінити на
  "калькулятор калорій для схуднення", "калькулятор денної норми калорій",
  "калькулятор ІМТ", "калькулятор відсотка жиру".

### 6.3 Перевірка PR 3

- Ручні запити `curl` до API: GET, POST, повторний POST з тієї ж адреси відхилений.
- `npm run build`; Rich Results Test показує Software App після 5 голосів.

## 7. Ризики і компроміси

- Без фото на мобільному hero виглядає інакше; зміну затверджено.
- GA з `lazyOnload` не рахує дуже короткі сесії.
- Елементи з `font-poppins` змінюють шрифт із системного на Inter.
- Прибирання поп-апу зменшує кількість показів Sytno; компенсується контекстним CTA.
- У PR 3 сторінка зі статичної стає ISR, кешування на edge зберігається.
- Суфікс бренду може обрізати частину заголовків `/learn`; налаштовується окремо.
